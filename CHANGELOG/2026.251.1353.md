# 2026.251.1353 — fix(appium): re-resolve the live Appium endpoint at bracket-open; hold brackets; clear stale session files (E-5)

## Summary

The E-5 recorder's evidence gate failed on the live bed (run 2026.251.1016): the start bracket never connected, zero brackets closed, row.json landed without the MP4 artifact. Three defects, one fix wave:

**Facet 1 — stale endpoint after the pod recycles (the E-5 1016 blocker).** The recorder dialed `sess.BaseURL` from the persisted session file (written once by session-create) and the host-side 4723 forward moves when the pod recycles — the recorder then dials the dead pre-recycle forward for the rest of the run (`dial tcp 127.0.0.1:38077: connection refused`, retried, then salvage 404s, zero brackets). Fix: at bracket-OPEN time the recorder RE-RESOLVES the current endpoint from the container's live forward — mirroring container.go's `appiumBaseURL` (same `<engine> inspect` resolution the plan's session-create used) — keeping the session file's SessionID (the bearer) and refreshing only the endpoint. The container name is spawn-stamped (`CHARLY_APPIUM_CONTAINER` = CheckEnv.ContainerName, the SAME container the plan's session-create steps resolve); when the stamp is absent, the venue's `podman-exec:` segment names the container (`CHARLY_APPIUM_VENUE=nested:podman-exec:charly-<box>/local`).

**Facet 2 — transient session-file vanish dropped the live bracket.** The old code salvaged (immediately stopped) the open bracket whenever the session file vanished, even transiently (baked suite's session-delete churn, runner phase sweeps). The premature `stop_recording_screen` 404'd against the still-live session and the row finalized `segments=0`. Fix: HOLD the open bracket while the file is missing — the finalize (done) or the next session change closes it against the still-live session.

**Facet 3 — stale session file cross-run contamination.** The ONE-identity fixture never deletes the session file (the baked delete is neutralized), so the NEXT run's recorder latched the PRIOR run's dead session/endpoint (run 1016: 147 connection-refused retries on the prior run's session id at its dead port). Fix: `session start` clears the stale session file before spawning the recorder — this run's session-create re-writes it before the recorder's bracket can latch anything.

**Facet 4 — session-file keying (R3).** E-5's ONE-identity fixture and this layer's baked av-suite were churning ONE shared session file: the baked suite's transient session (120s caps) rotated the same file and `delete-previous`-killed the fixture's pinned session under the open recorder bracket (runs 2026.251.1102/1122: final `stop_recording_screen` 404, row.json `segments=0`). Fix: a new optional `session_file` input on the appium verb — default is the SHARED box file (unchanged for every existing step); an explicit key resolves an ISOLATED file (`<box>_baked.json`). The baked lifecycle owns its own file; the two lifecycles cannot churn each other. The E-5 run's evidence proves the pair live: the fixture session 235cd9d6 stayed the ONE bracket through both feature phases while the baked delete rotated its own keyed file.

**Facet 5 — keyed create/delete aliasing (R5).** The legacy baked lifecycle's own `appium-session-create`/delete is DELETED; in its place, a `session_file: baked` keyed create ALIASES the live shared fixture session when one exists (returns the same SessionID, no server-side churn) and falls back to a fresh own session only when the shared one is dead; the keyed delete CLOSES only its own session — a keyed create alias is left alone (guarded via `sessionAlive`, the shared fixture session stays live for the recorder). R5: the stale plugin-side baked create/recorder/delete lifecycle is removed by this PR (see diff — dispatch.go alias branch + guard, w3c.go sessionAlive).
